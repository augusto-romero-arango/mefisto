## Problemas encontrados

1. **Los bloques de bash del markdown no se pueden portar.** Unos 350 bloques (96 usos de `jq`) corren desde comandos, agentes y skills; en Windows nativo Claude Code usa Git Bash para la herramienta Bash si Git for Windows está instalado y, si no, PowerShell. Un test que extrae un bloque de bash y lo ejecuta quedó como residual hasta el paso 7.
2. **Paridad con `jq` frágil**: jq 1.7 y 1.8 difieren (p. ej. `tonumber` sobre una cadena con espacios) y los runners traen versiones distintas, así que la paridad no puede depender de la versión.
3. **Matar al agente en Windows**: el runner usa `taskkill /PID <pid> /T /F` sobre el PID que lanzó, nunca por nombre.
4. **Defectos heredados del bash**: se portaron tal cual y fueron a borradores (#2571, #2572, #2576, #2579, #2581, #2589, #2591, #2600), salvo que en Windows rompieran algo.

## Lo que descartamos

- **Reescribir los bloques de bash del markdown en TypeScript o PowerShell.** Decisión del usuario: en Windows se exige Git for Windows (#2584, MEF-ADR-0057 decisión 9); los bloques se quedan en bash y solo se reemplaza lo que Git Bash no trae (`jq`, `python3`).
- **Corregir de paso los defectos heredados** dentro de los lotes: se mezclaría port con cambio de comportamiento.

## Aprendizajes

1. Un solo pipeline portado a fondo (`tooling`) sirve de molde: los demás se reducen a parámetros sobre módulos comunes.
2. La dependencia del toolchain se decide por lo que existe en el entorno mínimo (Git Bash), no por lo que sería ideal.
3. Portar y corregir son dos trabajos distintos; separarlos mantiene la paridad verificable.
